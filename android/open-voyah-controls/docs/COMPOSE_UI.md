# Compose routes and motion

Normal app screens share `MainActivity` and use Jetpack Compose. The root destination is the app grid: the **Open Voyah Controls** tile and installed apps appear directly, without a Back button, sidebar or page header. Settings, Buttons, voice settings, display, vehicle shortcuts, firmware maintenance, cluster maintenance and updates are destinations in the same host.

| Host | Responsibility |
| --- | --- |
| `MainActivity` | App grid, settings routes, app settings, assignments, permissions and maintenance workflows |
| `LaunchBrandActivity` | One-shot launcher animation in its own task |
| `QuickVoiceActivity` | Foreground voice popup, recognition state and text entry |
| `SetupActivity` | Installer/first-run handshake: a row per step with live status and elapsed time, the result and recovery actions (see [First-run check](DIAGNOSTICS.md#first-run-check)) |
| Private display `Presentation` | Media and navigation content in `DisplayPreviewScreen` |

Normal screens use explicit routes in `MainActivity`. The voice popup and installer handshake require a privileged permission for external callers. The application can open its own screens directly.

Tap the Android launcher icon to open Controls Settings. With reviewed panel assignments enabled, a short press on the central lower-left menu button opens the root app grid. The first tile, **Open Voyah Controls**, shows the app's own artwork and opens Settings on every desktop. It is the only Controls tile on a new grid; **Home screen and apps → App grid → Built-in shortcuts** adds shortcuts to individual Controls screens. Holding the panel button keeps the native launcher action. **Home screen and apps → App grid → App icon colors → Monochrome** draws app icons in the blue-white of the factory panel glyphs, in the grid and on the launcher panel's assigned buttons alike. When extra desktops are enabled, fresh grid entries open the saved default desktop. Detail destinations have Back navigation within the shared host.

Settings is a page of ten sections (`SettingsSection`), each with its own route. Sections built from groups use `SettingsSectionPage`: every group on one scrolling page (tags `settings_part_<KEY>`). A page that also exists on its own route is drawn inside a section with `LocalCockpitEmbedded`, which turns `CockpitDetail` into a heading and its content. Inside every `CockpitSection`, `CockpitGrid` puts controls marked with `Modifier.cockpitCell()` (switches, choices, compact sliders and chip rows) into as many columns as their measured content needs; anything unmarked keeps a full row. `ControlsNavigationViewModel.open(route, focus)` opens a section scrolled to a group; the Settings search uses it. A new setting goes into the group where a driver would look for it and gets an entry in `SETTINGS_INDEX`, so search finds it ([where the settings are](SETTINGS.md#where-the-settings-are)).

Android owns runtime permission dialogs, file selection, package-install approval, system settings, keyboard and toasts. The display destination embeds a native `SurfaceView` for the virtual display. Its `Presentation` and app dialog windows host `ComposeView` content.

Touching and holding an app tile opens **App settings** within the app grid destination; Back returns to the grid. Besides the launch, pin and window options, the page offers **Hide from the app list**, **Close app** and the app's **Permissions**, because the head unit firmware has no Android app info or permission screens. **Hide** shows the app's effective state: the user's choice (`hiddenApps`, `shownApps`) or else the default from `AppGridVisibility`, which hides firmware apps and their internal actions, the maker's apps, keyboards, service apps and extra launcher entries; **Settings → Home screen and apps → App grid → Hidden apps** lists every app with the same switch and says which of the two applies. Closing and permissions act only on apps installed on top of the firmware (`AppControlPolicy`): never on Controls itself, a preinstalled or maker app, the current launcher or keyboard, a device administrator, or an app with a system or shared identity. **Uninstall** (`pm uninstall` through the same channel, after a confirmation) follows the same rule; the page closes once Android no longer lists the package, and the grid reloads and says so for a few seconds in the page dots' row, which keeps its two rows. **Close app** also spares apps with an enabled accessibility service or notification listener, since Android 9 to 11 turn such an accessibility service off on a force stop. It asks for confirmation in the shared dialog, force-stops the app once through the authorized root channel and reports whether a process is left; a failed transport is checked against Android's stopped flag, and it is shown only while Android does not hold the app stopped. Permission switches grant or revoke a runtime permission with `pm`, and turn special access on or off with AppOps (display over other apps, modify system settings, install unknown apps, all files, usage access), writing the package mode and the numeric UID mode. Android 9 and 11 refuse another app's AppOps modes to an ordinary app, so a managed app's special access is read through the root shell as well. Each change is confirmed by reading Android's state back, never repeated, and the page shows an indeterminate bar while root work runs. Other apps' permissions are shown read-only, and Android's own pages appear only where the firmware resolves them; the car stubs that only answer "not available" do not count. The diagnostic log records `app_stop` and `app_permission_change` outcomes without package names.

## State and responsibilities

The existing Gradle modules retain logical MVVM and Clean Architecture boundaries. `core` contains Android-free command rules, button/session logic and ports. App `data` adapters own persistence, document serialization, Frida transport and privileged integration. Presentation ViewModels expose immutable state through StateFlow; Compose collects it using the destination lifecycle and handles local view state. Platform adapters and Android entry points handle permissions, intents, media, input and other operating-system events.

`ControlsNavigationViewModel` publishes the route stack, entry revision, and motion direction together. The stack and entry revision survive host recreation. Each animated destination receives its own lifecycle. The outgoing route drops to `CREATED`, leaves the accessibility tree, and stops accepting input during its exit. Route-owned dialogs and preview resources close when their owner stops or leaves. Confirmed maintenance work continues independently of navigation. Firmware and cluster maintenance use separate ViewModel keys in the shared host.

## Motion behavior

The shared palette uses neutral graphite surfaces, saturated blue actions, cool secondary text and restrained orange voice accents. Static cached lighting gives the background depth; it does not animate. App icons and labels have no background cards. Controls shortcuts and section icons use unboxed line artwork. Error feedback retains a separate coral role.

**Settings → Appearance** offers **Dark** and **Daytime** color themes. **High contrast** adjusts text, actions and outlines in either theme. **Text size** scales Compose typography together with Android's font size. **Spacing** adjusts page and card padding while keeping touch targets at their usual size. **Corner style** changes card, button and dialog shapes. **Start screen** selects the app grid, vehicle settings or general settings for the **Open Controls** shortcut shown when you hold the Android launcher icon. The app grid is the default for that shortcut. When a routine selects a theme for the session, dialogs and the voice popup follow it together with the screens, although they are hosted in their own windows. Running text never goes below 14 sp: the cockpit type scale defines every Material role that a screen uses, including field labels and card captions. Each option in the Appearance dialogs carries a small live sample (`AppearancePreviews.kt`, through the `preview` slot of `CockpitOptionDialog` and `CockpitOptionRow`): it is drawn with the same functions `ControlsTheme` uses (`cockpitColorsFor`, `cockpitTypography`, `cockpitShapes`, `cockpitLayout`, `cockpitWallpaperScrim`), so an accent shows its swatch and filled and outlined mini buttons in the current palette, a palette shows a miniature page, and the transition speed moves a dot with `CockpitMotion.routeDurations` and the settle easing; it stays still while screen transitions are off. Samples change color with `CockpitMotion.change()` and are hidden from accessibility, which reads the option's name. A custom accent (`cockpitAccentColors`) replaces the primary roles and also tints `secondary`, `outline` and `outlineVariant`, which the standard schemes draw in the default accent's blue grey; the tint keeps each color's luminance, so borders keep their contrast. Android's own widgets get the accent through a theme overlay (`controlsAccentOverlay`): `MainActivity` applies it to its window, and platform dialogs opened from Compose, such as the routine time picker, take it from `LocalControlsAccentOverlay`.

Screens are laid out for a canvas of at least 1280 × 480 dp, the 1920 × 720 central display at 240 dpi. Each activity applies `ControlsDensity` in `attachBaseContext`: it draws at the density that maps its display onto that canvas, and never below Android's own density. The head unit runs the display at 160 dpi, so Controls draws at 240 dpi there, and its screens, dialogs and popups keep the proportions of the emulator preview at 1.5 times the size Android's density would give them. Only Controls' windows change; the display and other apps keep their density. Screen sizes in dp are rescaled with the density, and app icons are rendered at the size of the largest grid icon at that density. The 240 dpi emulator already fits the canvas, so screen tests see no change.

A new app grid uses Large tiles, shaped after the factory launcher's grid: an 80 dp icon, a 19 sp caption and a 168 dp minimum cell, which gives six columns beside the launcher panel. Large rows share the page's height, so the central display shows exactly two whole rows; a page too short for two whole rows shows one. Compact and Standard tiles keep their fixed heights, and a saved tile size is kept.

**Lowered display.** When the motorised display slides down, Android keeps the full 1920 × 720 window, but only its top 560 px stay in sight. While it is lowered, the app grid ends its page dots inside that band and always shows two rows. When two rows of the chosen size do not fit, the rows share the height, and each tile scales its padding, icon, spacing and caption by the same factor so both caption lines stay visible. The normal display is laid out exactly as before, and the grid switches back as soon as the display rises. The state comes from the launcher agent's Settings.Global value `org.openvoyah.controls.screenLowered` (`1` lowered) and from the launcher's own `action.qg.layout.changed` broadcast; whichever arrives last wins (`rememberScreenLowered`, `LoweredScreen`). Without the agent, and before any broadcast, the grid keeps its normal layout. Other screens and other apps' windows are not changed.

The app catalog and the grid settings are loaded off the main thread when the process starts, after boot as well (`AppCatalogCache`), and loaded again when Android reports a package added, removed or changed; the first open of the grid shows that snapshot with its icons, custom icons, Hide state and pages at once and refreshes it quietly. The grid does not scroll vertically: it is a row of pages that a swipe turns one at a time and that snap into place (`PagedAppGrid`). A page holds the whole rows that fit, and `AppGridPages` fills them line by line the way a grid does, so a desktop card wider than the rest of a row starts the next row and, at the end of a page, the next page. The same pages hold search results, favorites desktops and every tile size. Dots under the grid show the page and open one on a tap; they take their row only when there is more than one page. A page turn follows **Transition speed** through `CockpitMotion`, happens at once with transitions off, and follows the animator duration scale.

**Move** in an app's **App settings** puts the grid into move mode with that app picked. Drag any app to a new place: the order previews under the finger, and holding the app at the left or right edge turns the page after a moment, so an app can travel to any page. In this mode a swipe drags apps rather than pages; the dots still open a page. The picked app has a ring around its icon and the tiles get no card behind them. A tap on another app puts the picked app there, and screen readers get **Move earlier** and **Move later** actions. The hint, the page dots and **Done** share the dots' row in this mode, so the pages keep their layout; Back or **Done** ends it, and cards and shortcuts stay in place without opening anything. Pinned apps stay ahead of the others on All apps, so a pinned app moves among pins and any other app among the unpinned ones. Moving an unpinned app saves a manual order (`sortOrder`, `manualAppOrder`) that keeps every other app where it was; on a favorites desktop a move reorders its pins. These are the settings the app grid already exports, imports and keeps in desktop layouts.

- Forward and Back use short, mirrored slides with a crossfade. External entries open their destination directly while Android handles the task transition. **Settings → Appearance → Animate screen transitions** controls in-app navigation and is enabled by default. **Transition speed** selects Short, Standard or Smooth and keeps the chosen speed if transitions are disabled. Navigation to or from the display screen switches immediately because its native preview surface cannot blend into a Compose transition on Android 9 and 11.
- A newly opened page lets its blocks arrive in order: each rises and fades in shortly after its neighbour, and the page settles within about half a second at the chosen **Transition speed**. A page you return to, a page redrawn after a language or theme change and the virtual display appear at once. The cascade follows **Animate screen transitions** and changes only the draw layer, so no text is measured again.
- Shared actions, navigation rows and app tiles use a 120 ms press response with a restrained scale change and surface feedback, and return with a short elastic settle. A row that is unavailable while work is running fades to its disabled strength instead of only ignoring the tap.
- Sections resize over 180 ms when their content changes. Status and result changes use short crossfades; first-run actions expand when available. A row that exists only while an option is on is revealed: it expands and fades in, and collapses the same way, instead of pushing the rows below it in one frame.
- Switching between a list and its editor (routines, if–then rules, the seasonal climate scenarios) slides the page a short distance in the direction of travel. The outgoing view keeps drawing its last state until it has left.
- Changing the palette, accent or contrast carries the page to the new theme instead of repainting it at once. Roles of two dark or two light themes blend over 260 ms. Between Dark and Daytime the content first dissolves into the page color, the page color changes, and the content emerges in its new roles, 420 ms in total, so text never passes through an unreadable grey. With the Daytime palette saved, the activity window itself opens light, so a start or a recreation shows no dark frame.
- App and command lists animate placement and appearance when their data changes. Assignment dialogs animate transitions between their steps. Reordering animates in the pinned-order, hidden-apps and favourites lists.
- The quick actions dock fades its shortcuts in when it opens and turns its chevron; selection, focus and accent changes blend. The reserved size and closing stay immediate, because a collapsed dock must return its strip to the page in the same frame.
- A live reading on the dock or on a desktop card (clock, track, road names, headlight mode, next service) crossfades when its value changes. A value that ticks, such as the distance to a turn, updates in place.
- Activity and dialog windows have finite entry/exit transitions. Every dialog uses one surface, width and motion. The voice popup tints its microphone tile by phase (listening, executing, failed), updates text within a phase in place, and shows a bar that empties over the actual listening window. The virtual display crossfades changed media/navigation content.
- The first-run check lists its steps with static status marks. A running step counts its own seconds from the time it started; the page clock ticks once a second only while a step runs, and the rows resize with the shared 180 ms change when agent rows appear.
- An operation that takes a while (a root command, firmware or cluster work, an update check) shows an indeterminate bar for as long as it runs. That bar marks real work and is the one animation that does not follow the transition setting.
- Compose honors Android's animator duration scale, including zero. Window transitions honor the corresponding system window/transition scales. There are no permanent decorative animation loops. Durations and easings come from one set of tokens (`CockpitMotion`: 120 ms press, 180 ms change, 240 ms enter, 110 ms exit), so a new screen cannot drift from the rest by picking its own numbers.
- During panel startup, the launcher agent checks for a visible assigned central button, the focused factory home screen and that no Controls setup page exists, even behind home. It records one launch request per Android boot before opening the animation. The animation starts on a solid background, opens the wings, then reveals the emblem, the app name and its tagline on the cockpit's own backdrop lights. The steel takes the accent chosen in **Appearance** once, with a single expanding ring. The finished mark then holds still for about 2.4 s before it leaves and the task returns to home; the timeline takes 4.5 s and a tap closes the intro. The hold is there because the intro appears only when the launcher agent is ready, about 40 s after the head unit starts, and a mark that left after one second was easy to miss.
- The intro is built to stay smooth while the head unit is still busy after boot. Its window is transparent and the intro draws the cockpit backdrop itself, over the whole window including the panel strip, so home stays on screen while the process starts cold. Before anything shows, the intro waits until 20 frames in a row arrive within two vsyncs, at most 5 s, and meanwhile draws the whole mark once per frame at an invisible alpha so text, paths and shaders are ready. Then the window takes touches, the backdrop fades in (240 ms), the timeline plays, and the backdrop fades out again. A late frame moves the timeline on by at most two frames, so a stall shows as a pause rather than a jump, and the timeline never falls more than half its length behind the clock. Start-up work that would compete for the CPU (the speech model and the app catalog) waits until the intro has closed, at most 20 s. The journal line `event=launch_brand outcome=played` (or `closed` after a tap, `interrupted` when another window took over) records `settle` (`steady` or `limit`), `settle_ms`, `frames`, `slow_frames`, `longest_gap_ms` and `elapsed_ms`.
- The intro always uses the dark roles, because it draws on the dark cockpit backdrop, and takes the accent, contrast and type choices from Appearance; it has no colors of its own. Disabling screen transitions or the system animator skips the intro. The agent can only see these conditions in a boot where it was started. Its `OVC_STARTUP_BRAND` line names what it did or why it skipped; see [What the JavaScript agents do](FRIDA_AGENTS.md#startup-intro).

State collection follows the destination lifecycle. Settings snapshots copy mutable preferences into immutable presentation state. The app grid decodes the selected desktop's saved image on an I/O worker. Playback progress derives from a timed media-session sample and ticks while the visible preview shows a playing track. The main Displays screen owns playback actions. Closing the display route releases its presentation, media-preview listener and virtual display.

Vehicle routines, seasonal climate, conditional rules and factory assistance use separate destinations and immutable ViewModel state. Foreground automation shares one native telemetry subscription and the established headlight monitor/history. Leaving the resumed host cancels observation and pending decisions. Each received snapshot owns finite signal-expiry deadlines; an absent source creates no timer. Settings archives contain configuration, while actual driving-mode history and activation evidence remain local. The Apollo candidate has no production writer or imported approval path. See [vehicle automation qualification](VEHICLE_AUTOMATION.md) and the [alternative candidate](APOLLO_CANDIDATE.md).

## Verification scope

Routing tests cover direct app-grid entry, explicit screen routes, internal Back, dialogs and host recreation. Manifest tests check the launcher and permission boundaries. The launcher test shows each stage of the intro as a fixed point of its timeline in the intro's own window and reads the pixels within the intro's own area (it starts right of the panel strip), checks that the charge follows the selected accent, and separately lets the animation run to see that it closes and returns to the previous task. Stages are not sampled from the running animation: a stage lasts a fraction of a second, and whether a screenshot lands inside it depends on the device. Document and permission returns are guarded by route lifecycle; the voice model also tests document-return sequencing. Compose checks inspect the actual app content tree and save real screenshots on explicitly isolated emulators. Android-owned permission and installation windows are separate from app content. App settings checks install an in-memory permission and close fixture under the grid's model key (`APP_SETTINGS_MODEL_KEY`) before the grid opens, so the confirmation, the close result and the switches are tested without a root channel; adapter tests read real packages and AppOps states on the emulator, and a long press on a real preinstalled app must offer no **Close app** and start with **Hide** on. Paging and move checks turn pages by swipe and by dot, drag an app with injected touch events across the page edge, and read the saved order. `ManagedAppPermissionsTest` runs the generated root scripts themselves (`pm`, `appops get` and `set`, `am force-stop` with its process wait) through adb's shell on the test package, which Controls manages, replacing only their root check.

Build/lint checks, screenshots and frame measurements answer different questions. Screenshots establish layout; interaction tests establish routing; bounded idle, hidden and animation-disabled measurements establish whether rendering settles on the tested emulator. They do not certify the frame rate or OEM behavior on a vehicle. Validation records apply to their listed revisions and completed checks; a source migration alone does not establish a new test result.
